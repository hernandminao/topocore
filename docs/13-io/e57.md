# E57

```text
E57 file
    │
    ▼
E57Reader  (streams per-scan, then per-chunk_size block within each scan)
    │
    ▼
E57Converter.from_scan()
    │
    ▼
   Chunk  (X, Y, Z, INTENSITY, COLOR — whichever the scan has)
    │
    ▼
PointCloud
```

**Read only.** The `e57` package's own docstring currently says
"readers and writers," but no writer exists in the codebase (only
`reader.py`, `base_reader.py`, `converter.py`) — treat E57 as
read-only until a writer is actually added.

Requires the optional dependency `pye57`.

## Reading

```python
from topocore.io.e57 import E57Reader

reader = E57Reader("scan.e57", chunk_size=100_000)
for chunk in reader:
    ...
```

**Unlike `LASReader`/`LAZReader`, `chunk_size` has no default here —
it's a required keyword argument.** Confirmed directly:

```python
>>> E57Reader("scan.e57")
TypeError: E57Reader.__init__() missing 1 required keyword-only argument: 'chunk_size'
```

## Multi-scan files

An E57 file can contain multiple scans (e.g. several tripod setups
in one project file). Each scan is read and chunked independently;
`Chunk.source_id` is set to the scan's own index within the file
(`0`, `1`, `2`, ...), so downstream code can tell which physical scan
a given chunk came from.

## Attribute mapping

| E57 field | `PointAttribute` |
|---|---|
| `cartesianX`, `cartesianY`, `cartesianZ` | `X`, `Y`, `Z` |
| `intensity` | `INTENSITY` (rescaled — see below) |
| `colorRed`, `colorGreen`, `colorBlue` (all 3 present) | `COLOR` (shape `(n, 3)`, combined) |

As with LAS, only fields actually present in a given scan are
included — confirmed directly with a real E57 file containing only
X/Y/Z and intensity: the resulting chunk had no `COLOR` attribute.

### Intensity is rescaled, not passed through raw

E57 has no fixed, universal intensity range — a file's `intensity`
field may be a raw sensor count, or (very commonly) already
normalized to `[0, 1]`. `PointAttribute.INTENSITY` is a unified
`uint16` field across every format TopoCore reads. Passing a
`[0, 1]`-normalized float directly into a `uint16` column would
truncate every value to `0`.

The converter rescales the scan's **own observed min/max** to fill
the full `[0, 65535]` range — not a fixed a-priori assumption about
E57's own `intensityLimits` metadata. Confirmed directly with a real
E57 file: an input intensity of `[0.108, ..., 0.9]` correctly spread
across roughly `[235, ..., 42841]` of the `uint16` range, proportional
to each value's position in the observed range.

**Degenerate case**: if every point in a scan has identical
intensity (including a single-point scan), rescaling by range would
divide by zero. Confirmed directly: this is handled by mapping every
value to the midpoint, `32767`, rather than raising or producing
`NaN`.

### Historical note: intensity/color used to be silently dropped

Until a fix confirmed in this project's own history, `_iterate_scans`
called pye57's `read_scan()` with its own bare defaults
(`intensity=False, colors=False`) — meaning intensity and RGB color
were never read from any E57 file, even when the file genuinely
contained them, despite the converter already being fully prepared
to extract both. This is now fixed: `read_scan()` is called with
`intensity=True, colors=True, ignore_missing_fields=True` explicitly.
The `ignore_missing_fields=True` flag matters too — without it,
pye57 raises `ValueError` for a missing, genuinely-optional field
(e.g. `cartesianInvalidState`), rather than simply omitting it.

## CRS detection — real, but unreliable in practice

`topocore.io.e57.crs_detection.detect_crs()` reads the file's own
`/coordinateMetadata` field and attempts to parse it as WKT, falling
back to a `.prj` sidecar if that fails — same priority as LAS/LAZ.
**This native path is genuinely less reliable than LAS's own**,
confirmed from 4 independent sources (the ASTM spec itself, MATLAB's
own documentation, a real-world writer's own source code, and
`pye57` itself): `coordinateMetadata` is a free-text field with no
enforced structure, and most real-world E57 writers never populate
it at all. In practice, `detect_crs()` returning `None` for a real
E57 file is the overwhelmingly common outcome — not a detection
failure, but a reflection of how rarely this field is actually
written. See [`crs-detection.md`](./crs-detection.md) for the full
detail and sourcing.

## Errors

```python
>>> E57Reader("missing.e57", chunk_size=1000).read()
PointCloudIOError: Unable to open E57 file 'missing.e57'.

>>> E57Reader("x.e57", chunk_size=0)
ValueError: chunk_size must be greater than zero.
```
